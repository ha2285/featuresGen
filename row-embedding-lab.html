Row Embedding Lab

A language model turns each table row into a list of 768 numbers. The usual approach adds those numbers to the table. Our method uses them only to find similar rows and adds about ten plain columns summarising how those rows turned out. Step through the method on real rows, replay the recorded experiment, then explore the results.

How to read this page

Each of the 19 tables is a prediction task: a yes/no question (e.g. “did this passenger survive?”) or a number to estimate (e.g. “how many points will this wine get?”). For every table we train a model several ways and compare how well it predicts rows it has never seen.

TermWhat it means on this page
Plain tableThe model trained on the table's own columns only, with no language model. Every other method is compared against it.
Improvement (gain)Score with a method minus score of the plain table. +0.05 = five points better on a 0–1 scale; a negative number means the method made things worse.
ScoreAUC for yes/no tasks (0.5 = guessing, 1 = perfect) and R² for number tasks (0 = no better than guessing the average, 1 = perfect).
SplitOne random division of a table into 80% training rows and 20% test rows. Each table is split 15 times and every result is averaged over the splits.
Free textA column of open-ended words, such as reviews, descriptions, titles or names, as opposed to fixed categories like “Boston”.
LightGBM / Linear modelThe two prediction models tested: a tree-based model that is the usual strong choice for tables, and a simpler logistic or linear regression.
MethodWhat it adds to the table
OursAbout 10 columns describing each row's 20 most similar rows, found with the language model (e.g. “how did similar rows turn out?”).
Embedding PCA-32The usual approach: the language model's 768 numbers for the row, shrunk to 32 columns.
Embedding fullThe usual approach without shrinking: all 768 numbers as columns.
Ours + PCA-32Both of the above together.
Word countsThe same ~10 columns as ours, but similar rows are found by shared words instead of the language model. Tests whether the language model is needed.
Original columnsThe same ~10 columns, but similar rows are found from the table's own columns, ignoring text. Tests whether the “similar rows” idea alone explains the gain.

Overall result: average improvement per table

Step 1, one table. Score the model on the plain table, then with the method's extra columns. The difference is the improvement. Example, wine reviews (LightGBM): plain table 0.405, with ours 0.591, so +0.186. Abalone: plain 0.540, with ours 0.519, so −0.021.
Step 2, all tables. Do this for all 19 tables and take the average. For ours that gives +0.035: a big win on a few text tables, small losses on many others.
During the replay only the splits finished so far are used, so the bars move at first and settle at these final values when all splits are done.

Results

All numbers are averages over the 15 recorded splits per table. Switch the model to see where the two learners disagree.

Ours helps as much as the usual approach, with far fewer added columns

Bar length = average improvement over the plain table across all 19 tables (the same number as in the replay).
Grey line under each name = how many extra columns the method adds to the table. Fewer columns means a smaller, faster model that is easier to inspect.

The improvement comes from tables with free text

The same average improvement as before, but computed separately for the 10 tables that have a free-text column and the 9 that do not. Full = all 768 embedding numbers; PCA-32 = 32 embedding columns; Ours = about 10 similar-row columns.

How to read it (LightGBM): on tables with text, every language-model method helps a lot. On tables without text they all make the model slightly worse, ours the least. Knowing what category names mean (e.g. job titles) did not help. With the linear model, ours also helps a little on tables without text.

More training rows, bigger gain on text

We re-ran the comparison with only 100, 300 or 1,000 training rows to see how much data the method needs. Choose which kind of table to show; the number in brackets is how many tables of that kind were large enough for this test.

LightGBM only

Meaning matters; number format does not

Two checks on why ours works. We re-ran it with the text changed in two ways:

  • Words scrambled: every word replaced by a made-up word. Repeated words still match, but meaning is gone. If the improvement disappears, the language model's understanding of meaning is what helps.
  • Numbers as digits: numbers written as “42” instead of words like “high”. Tests whether that design choice matters.

How to read it: scrambling the words removes the improvement with LightGBM and halves it with the linear model, so meaning matters. Digits instead of words make little difference. Based on the 7 tables with free text, first 1,000 rows of each.
